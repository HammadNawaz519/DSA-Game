1. GAMEPLAY CONCEPT & MULTIPLAYER DESIGN
====================================================================================================

1.1 1v1 PvP Mode: "Plants vs. Zombies: Tactical Warfare"
  - Player 1 (Plant Commander):
    * Defends the 5-lane lawn (5 rows x 9 columns).
    * Manages Sun Economy (Sun drops automatically + generated by Sunflowers).
    * Places defensive and offensive flora (Peashooter, Sunflower, Wall-nut, Cherry Bomb, Snow Pea, Jalapeno).
  - Player 2 (Zombie General):
    * Attacks the lawn to reach the house on the left.
    * Manages Brain Economy (Brains accumulate over time + earned by destroying plants).
    * Deploys zombie squads across any of the 5 lanes (Regular Zombie, Conehead, Buckethead, Newspaper, Flag Zombie).
  - Win Conditions:
    * Plants win if they survive all zombie assault waves or destroy the Zombie Crypt/Portal.
    * Zombies win if any zombie breaches the house (passes column 0 after bypassing lawnmowers).

1.2 2-Player Co-op Mode: "Allied Garden"
  - Both players defend the same 5-lane lawn against AI-driven server-calculated zombie waves.
  - Player 1 controls Lanes 1, 2, and top half of 3; Player 2 controls bottom half of 3, Lanes 4 and 5.
  - Shared or split Sun economy.

1.3 Client-Server Simulation & Tick Loop
  - Server Authoritative: All collisions, health deductions, sun production, and zombie movements are 
    verified by the authoritative C++ server at 20 ticks per second (50ms interval).
  - Client Prediction & Interpolation: Client renders animations smoothly at 60 FPS while interpolating 
    entity positions sent via authoritative server state packets.

3. BINARY FILE STORAGE ARCHITECTURE (NO DATABASES / NO JSON)
====================================================================================================

Every piece of persistent data must be saved to raw binary files on the backend filesystem using 
`std::fstream` with `std::ios::binary`. No SQLite, no MongoDB, no JSON, no CSV!

3.1 File Overview:
  1. `data/accounts.bin`    -> Fixed-size player records (Username, salted password hash, elo, coins).
  2. `data/config.bin`      -> System runtime configuration (8 settings + lock state).
  3. `data/replays.dat`     -> Append-only raw match replay actions.
  4. `data/replays.idx`     -> Index file mapping MatchID to byte offset in replays.dat.
  5. `data/archive.huff`    -> Huffman compressed match telemetry snapshots.

3.2 Magic Headers & Fixed-Size Record Formats:

File: `data/accounts.bin`
  Header Layout (16 bytes):
    [0..3]   : Magic Bytes: 'P', 'V', 'Z', 'A' (0x50565A41)
    [4..7]   : File Version (uint32_t, e.g., 1)
    [8..11]  : Record Count (uint32_t, total registered users)
    [12..15] : Record Size in Bytes (uint32_t = 64 bytes)
  Record Layout (64 bytes per user):
    [0..19]  : Username (char[20], null-padded)
    [20..51] : Salted SHA-256 / Custom Hash (uint8_t[32])
    [52..55] : ELO Rating (uint32_t, default 1000)
    [56..59] : Total Wins (uint32_t)
    [60..63] : Total Matches Played (uint32_t)

  O(1) Seek Formula:
    `byte_offset = sizeof(Header) + (record_index * sizeof(AccountRecord));`
    `file.seekg(byte_offset, std::ios::beg);`

File: `data/config.bin`
  Header Layout (8 bytes):
    [0..3]   : Magic Bytes: 'P', 'V', 'Z', 'C' (0x50565A43)
    [4..7]   : Version (uint32_t)
  Body (32 bytes):
    [8..11]  : zombie_speed_multiplier (float)
    [12..15] : sun_spawn_interval_sec (uint32_t)
    [16..19] : max_plants_per_row (uint32_t)
    [20..23] : action_rate_limit_x (uint32_t)
    [24..27] : action_rate_limit_y_sec (uint32_t)
    [28..31] : game_lock_state (uint32_t: 0 = active, 1 = frozen)
    [32..35] : start_sun_amount (uint32_t)
    [36..39] : zombie_health_multiplier (float)

File: `data/replays.dat` (Append-Only Log)
  Header (8 bytes): 'P', 'V', 'Z', 'R' + Version
  Action Record (24 bytes):
    [0..7]   : Timestamp in ms (uint64_t)
    [8..11]  : MatchID (uint32_t)
    [12..15] : PlayerID (uint32_t)
    [16..17] : ActionType (uint16_t: 1=PlacePlant, 2=SpawnZombie, 3=Shovel, 4=SunCollect)
    [18]     : Row (uint8_t)
    [19]     : Col (uint8_t)
    [20..23] : EntityID / CardID (uint32_t)

File: `data/replays.idx` (Index File)
  Enables O(1) jump into large replays without scanning:
  Record Layout (16 bytes per match):
    [0..3]   : MatchID (uint32_t)
    [4..11]  : Byte Offset in replays.dat (uint64_t)
    [12..15] : Total Events Count (uint32_t)

3.3 In-Memory Rebuild Pipeline on Startup:
  When the C++ server starts up:
    1. Read `config.bin` -> Load game balance settings and lock state.
    2. Read `accounts.bin` -> Insert users into Custom Hash Table (for O(1) auth) and AVL Tree (for live leaderboard).
    3. Read `replays.idx` -> Populate BST of completed games and Skip List of recent matches.
    4. Populate Bloom Filter with all registered usernames for instant collision check during signup.

4. CONTROL PANEL & ADMIN API (LIVE RUNTIME CONFIGURATION)
====================================================================================================

The university requires that game settings can be altered LIVE during the TA demo without restarting 
or recompiling the server.

4.1 Endpoints:
  - `GET /admin/config`:
    Headers: `Authorization: Bearer <ADMIN_TOKEN>`
    Returns JSON of all 8 settings + server uptime + active users count.
  - `PUT /admin/config`:
    Headers: `Authorization: Bearer <ADMIN_TOKEN>`
    Body:
    {
      "zombie_speed_multiplier": 1.25,
      "sun_spawn_interval_sec": 7,
      "max_plants_per_row": 5,
      "action_rate_limit_x": 10,
      "action_rate_limit_y_sec": 3,
      "game_lock_state": 0,
      "start_sun_amount": 150,
      "zombie_health_multiplier": 1.0
    }
    Action: Updates in-memory active config AND immediately writes to `config.bin`.
    Next request immediately adheres to the updated settings!

4.2 Game Lock / Maintenance Switch:
  - When `game_lock_state == 1`:
    * Server rejects all gameplay actions with HTTP 423 / WebSocket packet `ERROR: GAME_LOCKED_BY_ADMIN`.
    * Client displays a clear modal: "Lawn under maintenance by Administrator. Read-only mode."

4.3 Load Test Generator (Synthetic Traffic Bot):
  - Admin button: "Spawn 30 Virtual Players".
  - Runs a lightweight background thread on the server creating 15 virtual 1v1 rooms, placing plants, 
    and spawning zombies to demonstrate that the Circular Queue handles 30 concurrent users effortlessly.

7. NETWORK PROTOCOL & WEBSOCKET/HTTP API SPECIFICATION
====================================================================================================

7.1 REST HTTP API (Tier 2):
  - `POST /api/auth/register`
    Body: `{"username": "crazy_dave", "password": "supersecret"}`
    Check: Bloom filter -> If clean, write to `accounts.bin`, insert into Hash Table & AVL.
  - `POST /api/auth/login`
    Body: `{"username": "crazy_dave", "password": "supersecret"}`
    Returns: `{"token": "a98dfb67c4...", "username": "crazy_dave", "elo": 1000}`
  - `GET /api/leaderboard`
    Returns: In-order traversal array from AVL Tree (Top 50 players).
  - `GET /api/replays?match_id=102`
    Returns: Decompressed events using Huffman decoder & Skip List index.
  - `GET /admin/config` (Admin auth required)
    Returns: All 8 live settings.
  - `PUT /admin/config` (Admin auth required)
    Updates settings dynamically and flushes to `config.bin`.

7.2 WebSocket Protocol (`ws://<backend-host>/ws/game`):
  Every client sends and receives JSON packets with sequence IDs:
  
  Client -> Server Packets:
    1. Authenticate & Join:
       `{"type": "JOIN_MATCH", "token": "...", "role": "PLANT"|"ZOMBIE", "room_id": "Lawn42"}`
    2. Place Plant:
       `{"type": "PLACE_PLANT", "plant_type": 1, "row": 2, "col": 4, "client_time": 170000}`
    3. Spawn Zombie:
       `{"type": "SPAWN_ZOMBIE", "zombie_type": 2, "lane": 3, "client_time": 170005}`
    4. Collect Sun:
       `{"type": "COLLECT_SUN", "sun_id": 991, "client_time": 170010}`
    5. Undo Action:
       `{"type": "UNDO_LAST_ACTION", "client_time": 170012}`

  Server -> Client Broadcasts (20 Ticks/sec):
    1. State Sync:
       {
         "type": "TICK_UPDATE",
         "tick": 4820,
         "plants": [{"id": 10, "type": 1, "r": 2, "c": 4, "hp": 300}],
         "zombies": [{"id": 55, "type": 2, "lane": 3, "x": 780.5, "hp": 500, "state": "WALK"}],

8.1 Deploying the Backend on Render (Tier 2):
  Render allows running any Docker container with persistent disk storage.

  Step 1: Dockerfile (Inside `backend/Dockerfile`):
    ```dockerfile
    # Multi-stage build for optimal image size & speed
    FROM gcc:12 AS builder
    WORKDIR /app
    RUN apt-get update && apt-get install -y cmake make libpthread-stubs0-dev
    COPY . .
    RUN mkdir build && cd build && cmake .. && make -j4

    FROM debian:bullseye-slim
    WORKDIR /app
    RUN apt-get update && apt-get install -y libstdc++6 ca-certificates && rm -rf /var/lib/apt/lists/*
    COPY --from=builder /app/build/pvz_server /app/pvz_server
    RUN mkdir -p /app/data
    VOLUME /app/data
    EXPOSE 8080
    ENV PORT=8080
    CMD ["/app/pvz_server"]
    ```

  Step 2: Render Service Setup:
    - Log in to https://dashboard.render.com/
    - Click "New +" -> "Web Service".
    - Connect your GitHub Repository.
    - Root Directory: `backend`
    - Runtime: `Docker`
    - Instance Type: Free or Starter ($7/mo with persistent disk).
    - Add Persistent Disk (CRITICAL FOR BINARY STORAGE):
      * Name: `pvz-data-disk`
      * Mount Path: `/app/data`
      * Size: 1 GB (stores thousands of binary accounts, replays, and config).
    - Environment Variables:
      * `PORT`: `8080`
      * `ALLOWED_ORIGIN`: `https://your-pvz-frontend.vercel.app`
      * `ADMIN_SECRET`: `super_secret_dsa_token_2026`
    - Deploy! Your backend URL will be: `https://pvz-backend-xxxx.onrender.com`

8.2 Deploying the Frontend on Vercel (Tier 1):

8.3 The Required One-Line Restart Script:
  The course document states: "Up for the whole demo week, with a one-line restart script."
  Inside `backend/restart.sh`:
  ```bash
  #!/bin/bash
  # One-line graceful reboot script that flushes binary files and restarts daemon
  pkill -15 pvz_server || true && sleep 1 && /app/pvz_server >> /app/data/server.log 2>&1 &
  echo "[OK] PVZ Backend server restarted cleanly. Binary storage preserved."
  ```

9. VIVA DEFENSE GUIDE & TA SCENARIOS
====================================================================================================

The TA will ask tough questions during the 30-mark viva. Here are the exact scripted answers:

Q1: "Why did you use a Doubly Linked List for projectiles and zombies instead of a dynamic array?"
A1: "In Plants vs. Zombies, zombies die and peas explode frequently at random positions in the lane. 
     A dynamic array requires O(n) element shifting on deletion. A Doubly Linked List provides O(1) 
     node removal once we hold the iterator/pointer, eliminating memory reallocation hiccups during 
     intense 60 FPS combat."

Q2: "How does your Single-Worker Circular Queue protect data without mutex locking on every file write?"
A2: "Incoming multiplayer requests from all 30+ client WebSocket threads are pushed into our fixed-size 
     Circular Queue using an atomic index. A single dedicated worker thread pops and processes actions 
     sequentially. Because only ONE thread ever writes to `accounts.bin` and `replays.dat`, we achieve 
     complete thread safety and zero file corruption by design without expensive lock contention."

Q3: "Prove that your binary storage is O(1) seek and not sequential scanning."
A3: "Our `accounts.bin` utilizes fixed-size 64-byte records. To fetch the n-th player, we calculate 
     `offset = 16 + (n * 64)` and call `file.seekg(offset)`. We jump directly to the target byte 
     in exactly one disk seek operation without reading preceding records."

Q4: "Why use an AVL Tree for the leaderboard instead of a simple BST or sorting an array?"
A4: "Players are constantly scoring points. A basic BST can degrade to O(n) linked-list degenerate 
     shape if scores arrive in semi-sorted order. An AVL tree guarantees strict self-balancing via 
     rotations (LL, RR, LR, RL), maintaining strict O(log n) height for real-time rank inquiries."

Q5: "Where is BFS used versus DFS in your game?"
A5: "BFS is used for radially symmetric AoE blasts, such as the Cherry Bomb 3x3 explosion, exploring 
     concentric distance rings first. DFS is used for recursive chain reactions, such as Potato Mine 
     sympathetic detonations and Lawn Mower cascade triggers, traversing deep trigger trees to completion."
